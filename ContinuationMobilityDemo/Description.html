Migration View System View Description

What this demo shows

This is an executable model of continuation mobility in a distributed object system. It demonstrates how compute — not just data — can be suspended, moved between hosts, and resumed transparently, with full state recovery after a host failure. The canonical source is a single Rho script: Test/Language/TestRho/Scripts/ContinuationMobilityDemo.rho.

Background: KAI and the continuation model

KAI is a distributed object model for C++. Its executor is stack-based: execution state at any point in time is fully described by the contents of the stack plus the remaining continuation — the work still to be done. Because this state is serialisable, a suspended computation can be captured as a binary payload, transmitted over the network, and resumed on a different node with no change to the program logic. The computation doesn't know it moved.

This property — network-transparent continuation migration — is what the demo is modelling. The current implementation models the behaviour explicitly using agent snapshots and explicit restore logic. The intent is to show clearly what a fully integrated runtime would do automatically.

The world

The demo creates four logical regions, each hosted on a different node:

NodeA hosts the Start region — the initial placement for most agents.
NodeB hosts the Market region — high initial load, and the target of the failure drill.
NodeC hosts the Harbor region — Pi routes agents here when Market is congested.
NodeD hosts the Backup region — the load-balancing overflow and the recovery target.

Ten agents are distributed across Start, Market, and Harbor at initialisation. Each agent carries identity, region placement, step count, plan count, migration count, and a flag indicating whether it was recovered from a snapshot.

What drives agent movement

Agents move for three reasons, and the demo exercises all three in sequence:

Autonomous patrol. Every agent independently patrols adjacent regions. This models background compute that migrates for locality or resource reasons without external instruction.

Pi-guided routing. Every five steps an agent consults Pi, the planning language. Pi evaluates the current host load and can redirect the agent. In this demo, Pi detects Market congestion and reroutes the four Market agents to Harbor at tick 20. This models policy-driven migration: a planner decides where compute should run based on runtime conditions.

Load balancing. Every 25 ticks the world measures host load and shifts agents from the busiest host to the least loaded. This is the scheduler-driven form of migration — the system relocating compute to equalise resource pressure.

The failure scenario

The critical sequence runs between ticks 56 and 60:

At tick 56, a deterministic drill forces agents 1, 2, and 3 onto Market (NodeB). This makes the failure drill reproducible — the same three agents are always on the failed host regardless of where patrol and balancing have moved other agents. At tick 60, a snapshot of the full world is captured. NodeB then fails. Agents 1, 2, and 3 are removed from the live set. The snapshot is replayed: any agent whose snapshot region resolves to NodeB and who is not in the live set is reconstructed on NodeD with its full state intact — step count, plan count, migration history — plus a restored flag and an incremented migration counter. The world continues running with all ten agents present.

The recovery model is intentionally explicit. There is no magic. The snapshot is a plain data structure; recovery is a linear scan. This makes the mechanism inspectable and verifiable, which is the point of a reference implementation.

What the two views show

Migration View is the animated dot canvas. Each dot is a live agent. Transitions are animated as smooth movement between node positions. Orange rings identify restored agents. The phase strip tracks which phase of the scenario the simulation is in. Use this view to develop an intuition for how frequently and why agents move.

System View shows the same simulation as structured data — host and region state, agent lists, migration and plan counters, a timeline of key moments, and a rolling event log. Use this view to read the exact state at any tick and verify that recovery produces the expected outcome.

Relationship to the KAI runtime

This demo does not use the KAI executor, Registry, or network stack directly. It is a reference model: a clean, self-contained simulation of the intended behaviour that can be read, run, and tested without building the full framework. The canonical narrative lives in the Rho script; the HTML views are explanations of that narrative.

The next step — not yet implemented — is to wire the Rho script's migration events directly to real KAI continuation hooks, so that the Suspend / Migrate / Resume sequence in the demo becomes an actual cross-process continuation transfer over ENet UDP. The reference model exists precisely to make that target behaviour unambiguous before the plumbing is added.
